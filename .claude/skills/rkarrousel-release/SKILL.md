# RKarrousel release

Every new release (git tag `vX.Y.Z`) requires a freshly built `RKarrousel.exe`
built from the tagged commit. Never reuse an old `dist/RKarrousel.exe`.
No `Co-Authored-By` lines in commits (user preference).

## Versioning (semver, currently 0.x)
- `0.MINOR.0` for new features, `0.x.PATCH` for fixes. Go to `1.0.0` when the app is considered stable.
- Last release: check `git tag --sort=-v:refname | head -1`.

## How the exe reaches GitHub
Pushing a `v*` tag triggers `.github/workflows/release.yml` (Windows runner): unit tests, `build_windows.bat`,
a `--smoke-test` of the exe, the Inno Setup installer (`installer/RKarrousel.iss`, default settings in
`installer/default_config.json`), a silent install/uninstall test, then it creates the release (if missing) and uploads
`RKarrousel-vX.Y.Z.exe` and `RKarrousel-Setup-vX.Y.Z.exe`. The tag must equal `v` + `version.py` or the workflow fails.
Dry run without publishing: `gh workflow run release.yml --ref master` (installer kept as a run artifact).
The local build below is still needed to install the exe on the user's machine and as a fallback if CI fails.

## Auto-update contract (do not break)
The app updates itself from the latest GitHub release: `updater.py` looks for an asset named exactly
`RKarrousel-vX.Y.Z.exe` (portable exe, X.Y.Z = tag without `v`) and replaces the running exe in place (config untouched).
So every release MUST keep that asset name; the Setup asset is only for first installs. The repo is public, so the updater needs no token (token support was removed). A real self-update can be tested with two exes built from
different `version.py` values, a local fake GitHub (`RKARROUSEL_UPDATE_API`/`RKARROUSEL_UPDATE_REPO` env vars) and
`RKarrousel.exe --self-update log.txt`. NEVER stop test processes by name on the user's machine (see memory).

## Steps
1. Make sure the work is committed and pushed on `master` (`git status` clean apart from ignored/untracked build output)
   and that `python3 -m unittest discover -s tests` passes.
2. Pick the next version, set `__version__` in `version.py` (shown in the GUI title and the "À propos" dialog), commit and push it, then create an annotated tag on that commit: `git tag -a vX.Y.Z -m "vX.Y.Z - summary"`. The tag must never be created before the version bump.
3. Build the .exe from WSL using the Windows Python (`python.exe`/`py.exe` are on the PATH). `cmd.exe` rejects UNC paths,
   so build in a Windows folder from the tagged sources, then copy the result into `dist/`:
   ```
   W=/mnt/c/Users/riwal/AppData/Local/Temp/imagesplitter_build
   rm -rf $W && mkdir -p $W && git archive vX.Y.Z | tar -x -C $W
   (cd $W && cmd.exe /c build_windows.bat)
   cp $W/dist/RKarrousel.exe dist/RKarrousel.exe
   ```
   The final `dist/RKarrousel.exe` must always be the one built for the release being cut.
   Smoke-test it (builds the whole UI, then quits): `(cd $W/dist && ./RKarrousel.exe --smoke-test smoke.txt; sleep 3; cat smoke.txt)` must print `ok vX.Y.Z dnd=yes`.
4. Install locally for the user (their desktop shortcut points at the unversioned name): copy the new build into
   `/mnt/c/Users/riwal/Photos/imageSplitter/dist/` as TWO files, overwriting the old ones:
   `RKarrousel.exe` (stable name, used by the shortcut) and `RKarrousel-vX.Y.Z.exe` (versioned copy).
   Leave `.image_splitter_config.json` in that folder untouched (it holds the user's preferences).
   The copy over `RKarrousel.exe` fails with "Permission denied" if the app is running: ask the user to close it first,
   retry, then check with `cmp` that both files are identical.
5. Push the tag: `git push origin vX.Y.Z` (this starts the GitHub Actions release workflow).
6. Check the workflow (`gh` lives in `~/.local/bin`, add it to PATH): `gh run watch $(gh run list --workflow release.yml --limit 1 --json databaseId -q '.[0].databaseId') --exit-status`.
   If it failed or the asset is missing, fall back to a manual release:
   `cp dist/RKarrousel.exe dist/RKarrousel-vX.Y.Z.exe` then
   `gh release create vX.Y.Z dist/RKarrousel-vX.Y.Z.exe --title "vX.Y.Z" --notes "<changelog from git log since previous tag>"`
   (or `gh release upload vX.Y.Z ... --clobber` if the release already exists).
7. Confirm the release page lists `RKarrousel-vX.Y.Z.exe` and `RKarrousel-Setup-vX.Y.Z.exe` (`gh release view vX.Y.Z --json assets`). Release notes are auto-generated by CI;
   edit them with `gh release edit vX.Y.Z --notes "..."` if a readable changelog is wanted.
8. Ask the user to launch the app and check that the window title shows `vX.Y.Z` and that the "À propos" button shows the same version.

## Notes
- Repo: https://github.com/kerherve/RKarrousel (public since v0.8.0; renamed from imageSplitter, GitHub redirects the old URLs). Default branch: `master`.
- `build/`, `dist/` and `*.spec` are build artefacts, not committed.
- Local installer build (optional, Inno Setup 6 is installed per-user at `%LOCALAPPDATA%\Programs\Inno Setup 6`): copy `installer/` and `dist/RKarrousel.exe`
  to a Windows temp dir, then run `ISCC.exe /DAppVersion=X.Y.Z RKarrousel.iss` from a `.bat` (cmd quoting breaks otherwise).
- The Windows build needs `tkinterdnd2` (drag and drop); `build_windows.bat` installs it via `requirements.txt` and bundles it with `--collect-all`.
- GUI changes can be exercised on the real Windows Python from WSL (copy the project to a Windows temp dir and run `python.exe`); `PIL.ImageGrab.grab()` works there for screenshots.
